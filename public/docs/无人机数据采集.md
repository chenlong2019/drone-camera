# Cesium 无人机影像采集与三维场景重建技术方案（V1）

- **文档版本**：V1.0
- **状态**：第一版方案，供技术评审与开发拆分
- **适用项目**：基于 Cesium 的无人机模拟库
- **前端技术**：Vue 3 + TypeScript + CesiumJS
- **核心目标**：支持虚拟场景渲染图和真实无人机照片两类输入；浏览器侧采集/导入，后台异步重建，最终将成果回载至 Cesium 展示。
- **成果优先级**：优先视觉真实感；同时保留点云、网格模型等可用于空间分析的成果路径。Gaussian Splatting（3DGS）作为可选分支，不作为 V1 唯一交付格式。

---

## 1. 项目目标与边界

### 1.1 V1 要实现什么

1. 无人机在 Cesium 场景中飞行时，可以按任务配置采集虚拟影像，并保存每张影像对应的相机位姿、内参和场景信息。
2. 支持导入真实无人机照片及其 EXIF/GNSS 等元数据。
3. 两类影像进入统一的任务、上传、校验和后台处理流程。
4. 后台以异步任务执行摄影测量重建，生成稠密点云、网格/纹理模型等成果。
5. 将重建成果转换或发布为 Cesium 可加载的资源，支持浏览、显隐、定位和任务状态查看。
6. 为后续 3D Gaussian Splatting（3DGS）视觉重建预留处理分支和成果类型。

### 1.2 V1 不承诺什么

- 不承诺单张照片可以重建完整、唯一且准确的三维场景。
- 不承诺普通 GPS 照片可以达到测绘级绝对精度。
- 不在浏览器中执行大型 SfM/MVS 或 3DGS 训练；浏览器负责采集、预览、上传和结果查看。
- 不把 3DGS 当作精确的几何表面，也不默认它能直接参与可靠的射线求交、测距或点云采样。
- 不在 V1 实现大范围城市级持续增量重建、实时训练、自动修复所有失败任务。
- 不假设所有 Cesium 地形、3D Tiles 或外部模型都能通过同一种 API 获取任意射线交点。

## 3. 两类影像来源与处理策略

### 3.1 来源 A：Cesium 虚拟场景渲染图

虚拟影像的最大优势是相机位置、朝向、投影参数和场景坐标通常可直接获得。采集时应把图像与相机参数作为一个整体保存。

每张虚拟影像至少记录：

- 图像文件或 Blob。
- 采集时间、影像序号。
- 相机位置和朝向。
- 相机内参：图像宽高、焦距对应的像素参数、主点；若有镜头畸变模型也需记录。
- 坐标参考信息：椭球/地理坐标、场景局部坐标或项目定义的坐标框架。
- 场景版本或场景标识。
- 采集时的飞行器位姿、云台姿态（若使用云台）。
- 相机投影类型、视场角和近远裁剪等必要参数。

**实现注意：**

1. 不要只保存截图。截图必须与相机参数、时间戳和坐标信息绑定。
2. 截图前关闭或排除 UI、准星、调试辅助线、选中高亮等非场景内容。
3. 记录实际渲染相机，而不是仅记录无人机机身朝向；机身朝向和相机/云台朝向可能不同。
4. Cesium 场景截图可能受到地形、3D Tiles 层级加载、遮挡和渲染时序影响。应等待所需场景内容稳定后再采集，并记录采集质量状态。
5. 对已有准确模型的虚拟场景，若目标是获得该场景的三维模型，优先直接导出/复用原始几何，而不是把渲染图重新做摄影测量。影像重建更适合用于验证真实照片处理流程或模拟传感器流程。
6. 不能保证从任意 Cesium 截图都能稳定重建：纹理重复、动态对象、透明材质、天空、无纹理表面和视角重叠不足都会降低重建质量。

### 3.2 来源 B：真实无人机照片

支持用户上传照片目录/压缩包，或通过对象存储直传。尽量保留原始文件，不要在前端压缩后覆盖原图。

采集/导入时尽可能提取：

- EXIF 拍摄时间、相机型号、图像宽高。
- 焦距、35mm 等效焦距（若存在）、镜头信息。
- GPS 经纬度、高度（若存在）。
- 飞行器姿态、云台姿态、RTK 状态等厂商元数据（若能读取）。
- 原始文件名、文件哈希、文件大小。

**实现注意：**

- EXIF/GPS 信息不完整时仍可允许进入任务，但要标记元数据缺失。
- 普通 GPS 位置通常只适合初步地理定位；若需要较高绝对精度，应考虑 RTK/PPK、IMU 或地面控制点（GCP）。
- 真实影像与虚拟影像可以共用任务模型，但相机参数来源和坐标精度等级必须可区分。
- V1 先支持常见 JPEG；RAW、厂商专有格式和视频抽帧可后续扩展。

### 3.3 两种来源的统一原则

统一的是任务管理、影像清单、上传、状态、日志和成果查看；不应强行统一所有相机标定与坐标解算细节。

建议用 `source` 区分影像来源：

- `cesium-virtual`
- `real-camera`

并为坐标精度、相机参数来源和地理参考状态设置明确字段。

## 4. 后台重建处理管线

### 4.1 标准摄影测量管线（V1 主路径）

```text
创建任务
  ↓
上传/登记影像
  ↓
输入校验与影像质量检查
  ↓
相机参数读取/标定配置
  ↓
SfM：特征提取、匹配、相机位姿估计
  ↓
稀疏点云 + 相机位姿
  ↓
MVS：稠密点云重建
  ↓
可选：点云过滤、网格生成、纹理生成
  ↓
坐标配准 / 地理参考
  ↓
成果转换与切片（3D Tiles 或其他目标格式）
  ↓
发布成果清单
  ↓
Cesium 加载、预览与任务完成
```

**建议 V1 输出：**

- 处理报告与失败原因。
- 相机位姿/稀疏点云（用于诊断，可按配置决定是否保留）。
- 稠密点云（可选）。
- 网格模型及纹理（建议作为可测量几何成果路径）。
- Cesium 可加载的发布成果（优先 3D Tiles）。
- 坐标参考、范围包围盒、处理参数和成果文件清单。

不要把所有中间文件永久保留作为默认行为。建议配置保留策略：原始影像和最终成果长期保留，中间文件按任务配置或清理策略保留。

### 4.2 Gaussian Splatting 分支

```text
通过质量检查的多视角影像
  ↓
SfM / 相机位姿
  ↓
3DGS 训练
  ↓
质量检查、尺度/坐标对齐
  ↓
选择兼容的运行时或转换工具
  ↓
Cesium 端加载与性能验证
```

3DGS 适合追求照片级视觉观感的场景，但与网格模型的能力不同：

- 视觉效果可能很好，但不能直接等同于精确、闭合的三角网格。
- 物理测距、可靠碰撞、任意射线求交等能力不能默认成立。
- 地理坐标转换、尺度对齐、裁剪和大场景分块需要单独验证。
- 具体 Cesium 加载方式取决于选定的渲染器、插件或转换方案，必须做技术验证，不应假定标准 3D Tiles 一定原生支持所有 3DGS 表示。

因此建议 V1 先完成摄影测量主路径，再单独做 3DGS 技术验证和展示原型。

### 4.3 虚拟场景是否需要重建

应提供两种用途，避免把“截图重建”当作所有场景的唯一方案：

1. **算法验证模式**：用虚拟相机采集的影像进入 COLMAP/SfM/MVS，验证影像重建流程。
2. **原场景复用模式**：如果场景原本已有准确几何模型，直接复用原模型或转换为目标格式，避免重建导致精度和细节损失。

两种模式的结果应在 UI 中明确区分。

## 6. 前端模块接口建议

以下为建议的 TypeScript 契约，字段可根据现有项目类型调整。

### 6.1 基础类型

```ts
export type ImageSource = 'cesium-virtual' | 'real-camera'

export interface CameraIntrinsics {
  width: number
  height: number
  fx?: number
  fy?: number
  cx?: number
  cy?: number
  horizontalFovDeg?: number
  verticalFovDeg?: number
  distortion?: number[]
  calibrationSource: 'known' | 'exif' | 'estimated' | 'unknown'
}

export interface CameraPose {
  // 推荐使用明确的坐标系定义；不要只存一个含义不清的 position。
  position: [number, number, number]
  rotation: [number, number, number, number] // 四元数，需约定分量顺序
  coordinateFrame: 'ecef' | 'local-enu' | 'project-local'
}

export interface CapturedImage {
  id: string
  source: ImageSource
  fileName: string
  mimeType: string
  sizeBytes: number
  capturedAt: string
  imageUrl?: string
  localBlob?: Blob
  cameraIntrinsics?: CameraIntrinsics
  cameraPose?: CameraPose
  metadata: {
    latitude?: number
    longitude?: number
    altitude?: number
    cameraModel?: string
    sceneId?: string
    sceneVersion?: string
    dronePoseId?: string
    gimbalRotation?: [number, number, number, number]
    gpsAccuracyMeters?: number
    rtkFixed?: boolean
  }
  validation: {
    status: 'pending' | 'valid' | 'warning' | 'invalid'
    messages: string[]
  }
}
```

> `localBlob` 只用于浏览器内短期数据流，不应写入服务端数据库。上传完成后由服务端返回对象存储引用。相机坐标和四元数顺序必须在整个系统中统一定义。

### 6.2 影像采集服务

```ts
export interface CaptureSessionOptions {
  source: ImageSource
  name: string
  captureIntervalMs?: number
  distanceIntervalMeters?: number
  includeCameraMetadata: boolean
}

export interface CaptureSession {
  id: string
  options: CaptureSessionOptions
  status: 'created' | 'capturing' | 'paused' | 'finished' | 'failed'
  images: CapturedImage[]
}

export interface CaptureService {
  createSession(options: CaptureSessionOptions): Promise<CaptureSession>
  captureVirtualImage(sessionId: string): Promise<CapturedImage>
  importRealImages(sessionId: string, files: File[]): Promise<CapturedImage[]>
  pauseSession(sessionId: string): Promise<void>
  resumeSession(sessionId: string): Promise<void>

  getSession(sessionId: string): Promise<CaptureSession>

```

虚拟采集实现应由现有 Cesium Viewer 和相机状态提供者注入；不要让 `CaptureService` 自己创建第二个 Viewer。真实影像导入器负责解析元数据和生成统一的 `CapturedImage`。

### 6.4 成果与 Cesium 加载

```ts
export type ArtifactType =
  | 'sparse-point-cloud'
  | 'dense-point-cloud'
  | 'mesh'
  | 'textured-mesh'
  | '3d-tiles'
```

## 7. 后端 API 草案

| 方法   | 路径                                        | 用途                           |
| ------ | ------------------------------------------- | ------------------------------ |
| `POST` | `/api/capture-sessions`                     | 创建影像采集/导入会话          |
| `GET`  | `/api/capture-sessions/:id`                 | 获取会话与影像清单             |
| `POST` | `/api/capture-sessions/:id/images`          | 小文件或开发阶段上传影像       |
| `POST` | `/api/capture-sessions/:id/upload-sessions` | 获取大文件上传凭证/分片会话    |
| `POST` | `/api/capture-sessions/:id/images/complete` | 通知服务端上传完成并登记影像   |
| `POST` | `/api/reconstruction-tasks`                 | 创建重建任务                   |
| `POST` | `/api/reconstruction-tasks/:id/start`       | 启动任务                       |
| `GET`  | `/api/reconstruction-tasks/:id`             | 查询任务状态和进度             |
| `GET`  | `/api/reconstruction-tasks/:id/events`      | SSE 推送任务状态（可后续实现） |
| `POST` | `/api/reconstruction-tasks/:id/cancel`      | 请求取消任务                   |
| `GET`  | `/api/reconstruction-tasks/:id/artifacts`   | 获取成果清单                   |

### 7.1 上传建议

- 原型阶段可以经 API 上传少量图片，便于快速联调。
- 实际使用建议由 API 签发对象存储预签名 URL，浏览器直接上传文件，减少 API 服务的带宽和内存压力。
- 服务端应校验文件大小、MIME 类型、扩展名、影像数量和任务配额。
- 不信任浏览器上报的文件名、GPS、相机型号等元数据；服务端应重新校验或标记为用户提供的数据。
- 上传完成后以对象存储 key/asset ID 引用文件，不把图片二进制写进 PostgreSQL。

### 7.2 任务状态流转

```text
created
  → uploading
  → queued
  → running
  → publishing
  → completed

任意可取消阶段 → cancelled
处理失败       → failed
```

任务阶段建议细分为 `validate-images`、`sfm`、`mvs`、`mesh-texture`、`georeference`、`publish-tiles` 等。前端展示阶段和日志即可；不要在早期承诺各阶段百分比完全准确，除非底层工具能提供可靠进度。

## 8. 坐标系、相机模型与地理参考

这是整个系统最容易出现“成果能显示但位置不对”的部分，需要在 V1 明确约定。

### 8.1 坐标系约定

- Cesium 地球场景常用 ECEF（地心地固坐标）和经纬度/椭球高。
- 摄影测量软件内部可能使用局部坐标或由相机估计出的任意坐标系。
- 无人机姿态、相机姿态和重建软件相机姿态的轴向定义可能不同。
- 四元数分量顺序、旋转方向、右手/左手坐标系、角度单位必须写入代码契约和测试。
- 对虚拟影像，保存精确的场景坐标和相机姿态，并提供明确的坐标变换。
- 对真实影像，只有 GPS 不等于完成精确地理配准；必要时使用 RTK/PPK、控制点或其他外部约束。

### 8.2 地理参考模式

| 模式                    | 适用场景                 | 预期边界                                |
| ----------------------- | ------------------------ | --------------------------------------- |
| `local-only`            | 算法验证、无可靠定位数据 | 只能在局部坐标中查看                    |
| `camera-gps`            | 普通无人机照片           | 可用于粗定位，精度受 GPS 和姿态质量影响 |
| `rtk-ppk`               | 有高精度定位数据         | 需正确读取并应用相机曝光时刻的位置/姿态 |
| `ground-control-points` | 对绝对位置精度有要求     | 需要控制点坐标和影像中的对应关系        |

不要仅凭 `latitude/longitude/altitude` 三个字段就把任意重建结果直接放进地球坐标系。必须执行坐标解算、尺度/旋转/平移对齐，并记录所用方法和质量指标。

## 9. 算法边界与质量控制

### 9.1 影像质量检查

至少检查：

- 文件是否可解码、尺寸是否过小、是否重复。
- 模糊、曝光异常和明显遮挡（V1 可先做基础规则，复杂图像质量模型后续再加）。
- 影像数量是否达到所选处理流程的最低要求。
- 相邻影像的重叠度是否可能不足。
- 相机参数、GPS 和时间戳是否缺失。
- 是否混入视频帧、截图 UI、重复帧或大量天空/纯色图像。

### 9.2 重建失败要可诊断

失败结果至少记录：

- 失败阶段。
- 错误码和简短用户提示。
- Worker 日志引用。
- 可重试与否。
- 输入影像数量、成功注册相机数量等可获得的诊断数据。

不要只向前端返回“重建失败”。常见原因包括影像重叠不足、场景纹理不足、运动模糊、重复纹理、曝光差异大、相机参数不匹配和地理参考约束不足。

### 9.3 视觉成果与几何成果分开定义

| 成果        | 主要用途                      | 主要限制                             |
| ----------- | ----------------------------- | ------------------------------------ |
| 稀疏点云    | 相机解算诊断、稀疏结构预览    | 不适合当成完整表面                   |
| 稠密点云    | 形状观察、点云分析            | 数据量大，需过滤和分块               |
| 网格 + 纹理 | 视觉展示、部分测量/碰撞工作流 | 质量依赖影像和重建参数               |
| 3D Tiles    | Cesium 场景分块加载           | 需要正确转换、坐标和层级配置         |
| 3DGS        | 高真实感视觉展示              | 不等同于精确几何，运行时兼容性需验证 |

## 10. V1 页面功能范围

### 10.1 影像采集与导入面板

- 新建采集会话、命名和选择影像来源。
- 虚拟场景：开始/暂停/结束采集，设置定时或距离触发（V1 可先完成手动和定时）。
- 真实照片：多文件/文件夹导入，展示缩略图和元数据状态。
- 显示影像数量、有效/警告/无效数量。
- 支持移除无效影像、重新导入。
- 展示虚拟影像的相机位姿记录状态。

### 10.2 重建任务面板

- 选择影像集。
- 选择处理方式：摄影测量（V1 主路径）、3DGS（功能开关/实验入口）。
- 选择质量预设：预览、均衡、高质量。
- 选择输出成果：点云、网格、3D Tiles 等。
- 选择地理参考模式。
- 显示任务状态、阶段、日志摘要、失败原因和取消操作。

### 10.3 成果管理面板

- 展示成果类型、创建时间、文件大小（若可获得）、坐标参考和空间范围。
- 加载/卸载、显隐切换、定位到成果。
- 支持同一场景叠加查看原始 Cesium 场景和重建成果。
- 明确标识“原场景复用”“影像重建”“3DGS 视觉成果”，避免误认为成果来源相同。

## 11. V1 开发计划与验收

建议按可运行闭环分阶段推进，每个阶段结束都能演示。

### 阶段 1：影像数据与虚拟采集

**开发内容**

- 定义 `CapturedImage`、`CameraIntrinsics`、`CameraPose`。
- 对接现有 Cesium Viewer，采集虚拟渲染图。
- 保存相机内参、相机位姿、时间戳和场景标识。
- 支持真实 JPEG 导入和基础元数据读取。
- 建立影像集预览 UI。

**验收标准**

- 每张虚拟影像都能找到对应相机参数和坐标系信息。
- 真实照片可导入、预览并显示元数据缺失提示。
- 影像清单可导出为 JSON/CSV 或在开发日志中检查。

### 阶段 2：后台任务与摄影测量

**开发内容**

- 建立最小后端 API、影像上传和任务记录。
- 建立 Python Worker，执行影像校验与 COLMAP 流程。
- 记录阶段状态、日志、错误和处理产物。
- 先支持小规模测试数据集。

**验收标准**

- 可从前端创建任务并上传一组真实照片。
- 后台能完成或明确报告失败阶段。
- 刷新页面后仍可查询任务状态和成果记录。

### 阶段 3：成果发布并回载 Cesium

**开发内容**

- 输出并保存网格/点云成果。
- 建立成果清单与坐标元数据。
- 将支持的成果转换/发布为 Cesium 可加载格式，优先验证 3D Tiles。
- 实现成果加载、显隐、定位和卸载。

**验收标准**

- 已完成的任务可以从成果面板加载结果。
- 成果位置、朝向和尺度经过已知数据集验证。
- 大文件加载失败时有错误提示，不阻塞原有无人机飞行功能。

### 阶段 4：3DGS 可行性验证（不阻塞 V1 主路径）

**开发内容**

- 选择一组影像测试 3DGS 训练和成果导出。
- 验证 Cesium 端渲染方案、坐标对齐、裁剪、性能和显存/内存需求。
- 与网格/纹理结果进行视觉效果和交互能力对比。

**验收标准**

- 有一份可复现的端到端实验记录。
- 明确所选 3DGS 表示如何在当前 Cesium 版本中加载。
- 明确其不支持或不保证的几何分析能力。

## 12. 推荐的 V1 最小交付清单

优先完成以下闭环，不要一开始同时追求所有算法：

- [ ] 虚拟场景影像采集，并完整保存相机位姿与内参。
- [ ] 真实 JPEG 照片导入和元数据读取。
- [ ] 统一影像集和任务数据模型。
- [ ] 后台异步执行 COLMAP 摄影测量流程。
- [ ] 任务状态、阶段日志和失败信息。
- [ ] 输出至少一种可检查的重建成果。
- [ ] 发布并在 Cesium 中加载一种成果格式，优先验证 3D Tiles。
- [ ] 坐标系与尺度验证。
- [ ] 3DGS 作为独立验证分支，不作为首个里程碑的阻塞项。

### 首个端到端演示建议

使用一个纹理充足、视角重叠较好的小型场景或真实照片集：

1. 在浏览器中采集/导入影像。
2. 检查影像和相机元数据。
3. 创建后台重建任务。
4. 查看任务阶段与日志。
5. 获取重建成果。
6. 在 Cesium 中加载成果并与原场景对比。
7. 检查尺度、朝向、空间位置和视觉质量。

## 13. 主要风险与应对

| 风险                               | 影响                           | 应对策略                                                           |
| ---------------------------------- | ------------------------------ | ------------------------------------------------------------------ |
| 虚拟截图缺少真实相机参数           | SfM 无法稳定恢复正确相机       | 采集时同步保存相机内参、位姿与坐标系                               |
| 原场景几何本来就准确               | 重建反而损失几何质量           | 提供“原场景复用”和“影像重建”两种模式                               |
| 普通 GPS 精度不足                  | 成果位置漂移或尺度不准         | 记录精度等级，支持 RTK/PPK/GCP，允许局部坐标结果                   |
| 3D Tiles 坐标转换错误              | 模型位置、朝向或尺度异常       | 建立固定测试数据集和坐标变换单元测试                               |
| 大量影像占用存储和计算资源         | 任务排队、失败或成本上升       | 直接上传对象存储、任务配额、质量检查、可配置保留策略               |
| 3DGS 与 Cesium 兼容路径不确定      | 视觉分支延期                   | 先做独立技术验证，不阻塞摄影测量主路径                             |
| Cesium 场景射线/渲染结果受图层影响 | 虚拟采集或传感器模拟结果不一致 | 把场景查询与影像采集解耦，针对 terrain、3D Tiles、自有模型分别测试 |

## 15. 最终建议

V1 应优先解决“影像与相机参数可靠采集 → 后台重建可诊断 → 成果可回载 Cesium → 坐标和尺度可信”这条主链路。

**推荐实施顺序：**

1. 先把虚拟采集的数据契约做正确。
2. 再统一真实照片导入和影像集管理。
3. 用 COLMAP 建立可重复的后台摄影测量流程。
4. 将至少一种成果稳定发布并加载到 Cesium。
5. 最后评估 3DGS 的运行时、坐标与性能方案。

这样既能服务现有无人机模拟库，也能为后续 LiDAR 点云、倾斜摄影任务和多种三维成果管理保留扩展空间，同时避免第一版被过多算法和基础设施拖慢。
